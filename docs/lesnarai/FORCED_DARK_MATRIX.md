# Forced dark mode preservation: LESNAR AI theme contract and test matrix

Branch `portfolio/force-dark`, 2026-11-01/02. Owner requirement: "Forced Dark Mode Preservation".

## 1. Summary and acceptance status

**Contract.** Light: `#FFFFFF` backgrounds, `#000000` text, white cards. Dark: `#000000` backgrounds,
`#FFFFFF` text. The site's own theme choice must render exactly. No browser-generated grey,
charcoal or off-white.

**Status: NOT RELEASABLE. Blocked on the owner's Samsung Internet test (§4).** The Chrome Android
rows are also untested. The owner's standing rule also still applies: light mode stays
experimental until it has been tested on a real Samsung device.

**What is done:**
- Strict tokens. Both papers, both inks and the cards are pure, and the static gate enforces it.
- Explicit themes, declared to the browser three ways (§2).
- A probe page (`/lab/theme-probe/`).
- A pixel-measuring matrix across Chromium, Firefox, WebKit, and desktop Chromium with Blink's
  forced darkening.
- A screenshot analyser for phones.

**What the desktop evidence shows (§3):**
- All 18 required configurations pass on every measured cell, the real pages included.
- With Blink's forced darkening and a dark device preference (Chrome Android's documented
  condition), explicit LIGHT stays `#FFFFFF`/`#000000`, and SYSTEM shows the site's own dark theme
  untouched.
- Where a browser ignores `only` (Blink's FORCE_DARK_ONLY path, recorded with †), nothing the page
  declares prevents repainting, and even the dark theme loses detail.

Whether Samsung Internet behaves like the passing rows or like † is **unknown**. No primary source
settles it (§5). Only the device test can.

- Fills use the median of the cell.

**What the numbers say.**
1. **Required configurations: all pass.** That includes explicit LIGHT under Blink force-dark with a
   dark preference: `color-scheme: only light` is honoured.
2. **The † path repaints everything.**
   - Explicit LIGHT: page and cards `#FFFFFF → #121212`, text `#000000 → #FFFFFF`, signal
     `#D41F1A → #FF593F`, text field `#FFFFFF → #121212`, the 50% overlay `#808080 → #090909`.
   - Explicit DARK still loses detail: the white stage icon `#FFFFFF → #121212` (invisible on
     black), map land `#1E2620 → #EBF6ED`, signal `#FF4A3D → #E32C2A`, meta text
     `#8F9296 → #73767A`, the primary button `#FFFFFF → #121212`.
3. **Images depend on density.**
   - In the † path at DPR 2 and above, Blink inverted raster images: a white tile became `#000000`,
     a black tile `#FFFFFF`, and the light CarePro capture's mean went `#E4E3E1 → #79776D`.
   - At DPR 1 the same images were untouched.
   - This is why the matrix runs at phone density. A desktop-density run under-reports what a
     phone shows.
4. **None of the three Samsung workaround candidates survives Blink's override.**
   - A raster tile as paper inverts at phone density.
   - Text over the raster tile turns white, which would be invisible if the tile survived.
   - A gradient paper darkens to `#121212`.
   - None is used in site CSS. They stay on the probe for the device test only.
5. **Native select and checkbox** paint the browser's own field colours: Chromium `#3B3B3B` in
   dark, Firefox `#E9E9ED`/`#2B2A33`, WebKit `#F4F4F4`/`#343434`. They are observed, not judged:
   the site uses neither. Its text field, textareas and button are styled and pass.

## 5. Research findings

Primary sources first. Developer reports are marked as such and treated as unverified.

**Chromium Auto Dark Theme and the `only` keyword**
- Chrome's own documentation, <https://developer.chrome.com/blog/auto-dark-theme>:
  - Auto Dark Theme "applies an automatically generated dark theme to light themed sites, when the
    user has opted into dark themes in the operating system".
  - Opt-out is `<meta name="color-scheme" content="only light">`, which "prevents Auto Dark Theme
    from being applied at all" and avoids a flash of darkened content, or `color-scheme: only
    light` in CSS, per element or on `:root`.
  - Detection: a `canvas` background under `color-scheme: light` computes to non-white when Auto
    Dark is active. The probe's readout uses this.
  - Android test path given there: `chrome://flags/#darken-websites-checkbox-in-theme-setting`,
    then Settings → Theme → "Apply Dark themes to sites, when possible".
- CSS Color Adjustment Level 1, <https://drafts.csswg.org/css-color-adjust-1/>:
  - §2.2: `only` "Forbids the user agent from overriding the color scheme for the element".
  - §2.5: for pages that declare dark support, a forced dark mode "has no effect other than
    reporting a dark value for the prefers-color-scheme media query".
- Blink source:
  - <https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/style/computed_style.cc>,
    `ComputedStyleBuilder::SetUsedColorScheme`: forced darkening applies when
    `force_dark && !has_only`, **and also when `force_dark && !prefers_dark`** ("to support the
    FORCE_DARK_ONLY behavior from WebView"). With a light preference, `only` does not protect the
    page. Measured: this is the † path.
  - Paint uses `ComputedStyle::ForceDark()` = `DarkColorScheme() && ColorSchemeForced()`
    (`computed_style.h`, `paint/paint_auto_dark_mode.h`).
  - Darkening thresholds: foreground brightness 150 and background brightness 205
    (`platform/graphics/dark_mode_settings_builder.cc`).
  - `css/style_engine.cc` notes that with forced dark "the preferred color scheme can be light while
    the setting is dark".

**Chrome Android "darken websites"**
- <https://github.com/chromium/chromium/blob/main/chrome/browser/chrome_content_browser_client.cc>:
  - On Android the page's preferred scheme is dark when `theme_client->IsNightModeEnabled()`.
  - `force_dark_mode_enabled` comes from `theme_client->IsForceDarkWebContentEnabled()`.
- Not found in code: whether force-dark can be on while Chrome's night mode is off. Chrome's
  documentation (above) says darkening applies when the user has opted into dark themes. Under that
  documented condition the page prefers dark, so `only light` is honoured (the passing force-dark
  rows). C1/C2 confirm or refute it on a device.

**Samsung Internet**
- Samsung's own blog, 15 Dec 2020,
  <https://developer.samsung.com/internet/blog/en-us/2020/12/15/dark-mode-in-samsung-internet>:
  - Samsung's dark mode "applies its own transformations upon the colors provided by the web
    developers".
  - Samsung 13.2 Beta added `prefers-color-scheme` and the `color-scheme` meta tag and property.
  - An experimental `internet://flags` option "Force Dark Behavior" has three settings: Force Dark
    Only, Media Query Only, and Prefer Media Query Over Force Dark. The last only works when the
    page declares its schemes, e.g. `<meta name="color-scheme" content="light dark">`.
  - The blog does not mention `only`, any site opt-out, the default setting, or how images are
    treated.
- Developer reports, unverified:
  - <https://www.v01.io/posts/2024/04/samsung-internet-dark-mode/> (2024, updated): by default
    Samsung's dark mode "ignores CSS for prefers-color-scheme: dark", renders the light CSS and
    transforms it. An experimental `internet://flags/#enable-adaptive-force-dark` (beta v26+)
    "respects the preferred color scheme"; its release date was unknown.
  - <https://matt.sibson.link/blog/samsung-dark-mode>: Samsung's dark mode "doesn't mess with
    images", and the author worked around it with raster backgrounds for Samsung user agents.
  - <https://forum.developer.samsung.com/t/websites-dark-mode-gets-overridden-by-samsung-internets-dark-mode/22937>:
    a long thread with conflicting reports. This forum could not be read directly (its JSON and
    HTML endpoints no longer serve the thread). Search summaries mention `color-scheme` meta
    support from v24.0.6.15 and a Labs "Use website dark theme" toggle; both are unverified.
- **Missing sources.** I found no Samsung primary documentation on any of these:
  - whether current Samsung Internet honours `color-scheme: only light` or `<meta … "only light">`;
  - what its current default force-dark behaviour is;
  - whether it recolours raster images.
  These are exactly what rows S1–S3 decide. Nothing in this document infers them.

## 6. Limitations

- **A browser that ignores `only` cannot be stopped.** This covers Blink's FORCE_DARK_ONLY path
  (measured), and possibly Samsung's default dark mode (developer reports). No CSS, meta tag or
  colour choice prevents the repaint. Pixel accuracy is then impossible for the light theme, and
  partly impossible for the dark theme (icons, map fills, signal red and buttons all changed in †).
- **Images are not safe under such an override at phone density.** Blink inverted raster images at
  DPR ≥ 2. Rasterising text is excluded by the owner's rules, and the measurement shows it would
  not help: the raster gets inverted too.
- **Workarounds that only work by detecting a browser are excluded until a device proves them.**
  User-agent sniffing plus raster or gradient backgrounds is what developers report for Samsung.
  The probe carries those candidates for the device test only.
- **Native select and checkbox colours belong to the browser.** They're outside the contract, and
  the site uses neither.
- **Without JavaScript only SYSTEM works.** An explicit LIGHT or DARK choice needs the bootstrap.
  SYSTEM declares `light dark`, which spec-following browsers resolve to the site's own theme.
- **The probe readout detects only Chrome's Auto Dark Theme.** Samsung's transformation may not be
  detectable from the page at all. The screenshots are the evidence.
- **Desktop results are evidence, not the release criterion.**
