Flagship · commerce and operations

Gen-Eat +and Hazina Nomads

Two very different businesses — campus food and private luxury sourcing — began on one shared multi-tenant backend and were separated into independently deployable product runtimes with isolated databases, credentials, Redis namespaces, health checks and proven failure domains.

  • LIVE · PILOT Gen-Eat storefront Reachable, verified 2026-08-07
  • LIVE Hazina Nomads storefront Reachable, verified 2026-08-07
  • LIVE Two independent product APIs geneat-api and hazina-api answering over HTTPS, verified 2026-08-09
  • NOT CURRENTLY REACHABLE Model-backed conversation No language-model credential configured, verified 2026-08-09

    1. Conversation. A customer states intent in the channel they already use.
    2. Catalog. Intent is matched against what can actually be sold right now.
    3. Payment. Settlement runs through a provider-agnostic interface.
    4. Routing. The order reaches the person or merchant who must fulfil it.
    5. Fulfilment. The physical outcome happens and status becomes observable.
    6. Recovery. Anything that did not go to plan is escalated to a person.

    Evidence

    The two products were one multi-tenant backend. They have since been separated into independent runtimes that share no database, no credentials and no process.

    Type
    Repository architecture · migration
    Source
    Historically app/db/models.py defined Business as “a tenant — each SME using the platform”, and both portals resolved the same BACKEND_URL. Each product now owns its own extraction, database (geneat_prod, hazina_prod), database user, Redis namespace, migration history and service unit.
    Verified
    2026-08-09 · each database user was proved unable to connect to the other’s database; Redis namespaces are mutually invisible; each suite passes independently — 183 and 284 tests. Stopping either API returns 502 for that product alone through the public edge, while the other product and a third unrelated application on the same host keep serving.
    Limit
    One host, one PostgreSQL engine, one Redis server: the infrastructure is shared, the application runtime is not. No historical operational data was migrated — both databases start empty. Generic modules are duplicated rather than shared, and that duplication will drift.

    The original hosted backend is not currently running. Its two independent replacements are, on a different host, behind their own public addresses.

    Type
    Reachability probe
    Source
    Two health endpoints, inspectable directly — both return {"status":"ok"} over HTTPS: Gen-Eat API health check — opens in a new tab Hazina API health check — opens in a new tab
    Verified
    2026-08-09 · resolved consistently by the authoritative nameserver and two independent public resolvers. The predecessor endpoints still return a DNS misconfiguration and a suspended service respectively.
    Limit
    A health check proves the process answers, not that the product works. Conversation is not exercised: neither runtime holds a language-model credential, so no reply is generated. Administrative and introspection surfaces are deliberately unreachable from these hostnames.

    The difficult part

    Two businesses with almost nothing in common — a campus café serving students between lectures and a private sourcing house shipping heritage pieces abroad — have to share catalog, payment and routing without either inheriting the other's assumptions. The tenant boundary was the whole design: currency, hours, escalation and brand voice are per-business data, so adding a business was configuration rather than a fork. Separating the two products tested that claim and found it only partly true — tenant-specific branches had leaked into the channel adapter that both products depend on, so the “shared core” was never as clean as the module names suggested. Splitting them is what surfaced it.

    What is not proven here

    No usage, revenue, order volume or customer count is claimed — none was measured, and a reachable page proves none of it. The conversational path was not exercised end to end: the separated runtimes answer their health checks but carry no language-model credential, so no reply was generated. Gen-Eat's in-page chat proxies to a documented test surface, not the production ordering channel; the production channel is WhatsApp.

    One request, all the way through

    Each stage names what enters it, what acts, what can fail, and what recovery exists. The module paths are the ones that implement it in the repository.

    01 Request

    Enters
    An inbound message or call from a customer channel.
    Acts
    app/api/whatsapp.py, app/api/voice.py, app/channels/base.py
    Can fail
    Webhook signature mismatch, provider retry storms, duplicate delivery.
    Recovery
    Idempotent handling; the channel adapter contract keeps provider quirks out of business logic.

    02 Context

    Enters
    The message, plus whatever this customer was already doing.
    Acts
    app/services/conversation_context.py, session_manager.py, language.py
    Can fail
    Lost session state; a returning customer treated as new; wrong language.
    Recovery
    Session state is reconstructed rather than assumed, and language is resolved per turn.

    03 Decision

    Enters
    Intent plus context.
    Acts
    app/services/conversation_service.py, hazina_deterministic_gate.py, output_sanitizer.py
    Can fail
    A model producing a confident answer it should not give.
    Recovery
    A deterministic gate constrains what may be said, and output is sanitised before it reaches a customer. The model does not get the last word.

    04 Payment

    Enters
    A validated order awaiting settlement.
    Acts
    app/integrations/payments/factory.py, daraja.py, intasend.py
    Can fail
    STK push never confirmed; callback arrives late, twice, or not at all.
    Recovery
    Provider-specific behaviour is isolated behind one interface, so a stalled payment is a known state rather than an unhandled branch.

    05 Routing

    Enters
    A paid order that a human now has to fulfil.
    Acts
    app/services/staff_dispatch.py, outbox.py, webhook_dispatcher.py
    Can fail
    Notification lost; a merchant never sees the order.
    Recovery
    Outbound work goes through an outbox rather than a fire-and-forget call, so delivery survives a restart.

    06 Recovery

    Enters
    Anything that did not go as planned.
    Acts
    app/services/hazina_escalation.py, hazina_customer_fallbacks.py, order_tracking.py
    Can fail
    Silent failure — the worst outcome, where nobody is told anything.
    Recovery
    Escalation paths hand the conversation to a person, and the customer is told what is happening.

    Every stage is readable here as plain content. Wave F turns this into a keyboard-navigable inspector; nothing in that wave may become the only route to this information.

    Software becomes physical action

    The same discipline applied past the screen: observation, evidence, a confidence boundary, a person who decides, and only then a machine that moves.

    PROTOTYPE — engineering demonstration

    1. Observe. A camera frame is captured as a package passes.
    2. Detect. A model proposes that the package may be damaged.
    3. Verify. Confidence and supporting frames are assembled and checked against a threshold. Below it, nothing is actuated.
    4. Approve. A person confirms or rejects the proposed action.
    5. Command. A control instruction is issued to the diverter.
    6. Act. The package is diverted to an inspection lane.
    7. Record. The operational record is updated with what was decided and why.

    Labelled a prototype because that is what the evidence supports. No production computer-vision system, no deployed robotics, and no recorded operational run backs this sequence.

    Current limitations of this prototype

    • No motion yet. Waves A and B build the static narrative only. The Effects control is wired and persists a choice, but there is currently no animation for “Reduced” to reduce.
    • The inspector is not interactive. All six stages are shown at once. Stage selection, keyboard locking and the text-alternative pairing arrive in Wave F.
    • No measured outcomes. No Gen-Eat metrics, adoption figures, payment volumes or performance numbers appear anywhere on this page, because none have been measured in this wave.
    • Live status is inferred, not probed. The LIVE label rests on the production landing linking the product and on the deployment target declared in this repository. No request was made to the running service.
    • No physical deployment. The action sequence describes an engineering demonstration. Nothing here claims a deployed robotics or computer-vision system.
    • Not comparable to Study B yet. Neither prototype has visual or motion work, so no score under the comparative framework is available.
