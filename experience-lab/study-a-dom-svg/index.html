Gen-Eat

LIVE

Ordering food in Nairobi happens in conversation, not in an app store. Gen-Eat treats the chat thread as the interface: a customer orders in the channel they already use, and the system behind it handles catalog, validation, payment, dispatch and recovery.

Architecture

Verified — read from this repository

Backend
FastAPI service under app/, Alembic migrations, Postgres and Redis.
Channels
Adapter contract in app/channels/base.py with WhatsApp, voice and mock implementations behind a registry — the channel is swappable, not hard-wired.
Payments
Provider factory in app/integrations/payments/: M-Pesa Daraja, IntaSend, Paystack, Stripe and a simulator behind one base.py interface.
Storefront
Next.js app router portal in gen-eat-portal/, deployed on Vercel.

Technical decision

Verified — read from this repository

Payment providers sit behind a factory rather than a direct SDK call. Kenyan mobile money and card rails fail differently and change terms independently; a system that hard-codes one provider has to be rewritten when that provider changes, and cannot be tested without touching live money. The simulator adapter exists for exactly that reason.

Deployment

Verified — read from this repository

Infrastructure is declared in render.yaml: a Docker web service with a managed Postgres instance and a Redis key-value store, all in the Frankfurt region. The storefront is a separate Vercel project; the production landing links the product at geneat.lesnarai.co.ke and the portal targets api.lesnarai.co.ke.

One request, all the way through

Each stage names what enters it, what acts, what can fail, and what recovery exists. The module paths are the ones that implement it in the repository.

01 Request

Enters
An inbound message or call from a customer channel.
Acts
app/api/whatsapp.py, app/api/voice.py, app/channels/base.py
Can fail
Webhook signature mismatch, provider retry storms, duplicate delivery.
Recovery
Idempotent handling; the channel adapter contract keeps provider quirks out of business logic.

02 Context

Enters
The message, plus whatever this customer was already doing.
Acts
app/services/conversation_context.py, session_manager.py, language.py
Can fail
Lost session state; a returning customer treated as new; wrong language.
Recovery
Session state is reconstructed rather than assumed, and language is resolved per turn.

03 Decision

Enters
Intent plus context.
Acts
app/services/conversation_service.py, hazina_deterministic_gate.py, output_sanitizer.py
Can fail
A model producing a confident answer it should not give.
Recovery
A deterministic gate constrains what may be said, and output is sanitised before it reaches a customer. The model does not get the last word.

04 Payment

Enters
A validated order awaiting settlement.
Acts
app/integrations/payments/factory.py, daraja.py, intasend.py
Can fail
STK push never confirmed; callback arrives late, twice, or not at all.
Recovery
Provider-specific behaviour is isolated behind one interface, so a stalled payment is a known state rather than an unhandled branch.

05 Routing

Enters
A paid order that a human now has to fulfil.
Acts
app/services/staff_dispatch.py, outbox.py, webhook_dispatcher.py
Can fail
Notification lost; a merchant never sees the order.
Recovery
Outbound work goes through an outbox rather than a fire-and-forget call, so delivery survives a restart.

06 Recovery

Enters
Anything that did not go as planned.
Acts
app/services/hazina_escalation.py, hazina_customer_fallbacks.py, order_tracking.py
Can fail
Silent failure — the worst outcome, where nobody is told anything.
Recovery
Escalation paths hand the conversation to a person, and the customer is told what is happening.

Every stage is readable here as plain content. Wave F turns this into a keyboard-navigable inspector; nothing in that wave may become the only route to this information.

Software becomes physical action

The same discipline applied past the screen: observation, evidence, a confidence boundary, a person who decides, and only then a machine that moves.

PROTOTYPE — engineering demonstration

  1. Observe. A camera frame is captured as a package passes.
  2. Detect. A model proposes that the package may be damaged.
  3. Verify. Confidence and supporting frames are assembled and checked against a threshold. Below it, nothing is actuated.
  4. Approve. A person confirms or rejects the proposed action.
  5. Command. A control instruction is issued to the diverter.
  6. Act. The package is diverted to an inspection lane.
  7. Record. The operational record is updated with what was decided and why.

Labelled a prototype because that is what the evidence supports. No production computer-vision system, no deployed robotics, and no recorded operational run backs this sequence.

Current limitations of this prototype

  • No motion yet. Waves A and B build the static narrative only. The Effects control is wired and persists a choice, but there is currently no animation for “Reduced” to reduce.
  • The inspector is not interactive. All six stages are shown at once. Stage selection, keyboard locking and the text-alternative pairing arrive in Wave F.
  • No measured outcomes. No Gen-Eat metrics, adoption figures, payment volumes or performance numbers appear anywhere on this page, because none have been measured in this wave.
  • Live status is inferred, not probed. The LIVE label rests on the production landing linking the product and on the deployment target declared in this repository. No request was made to the running service.
  • No physical deployment. The action sequence describes an engineering demonstration. Nothing here claims a deployed robotics or computer-vision system.
  • Not comparable to Study B yet. Neither prototype has visual or motion work, so no score under the comparative framework is available.
